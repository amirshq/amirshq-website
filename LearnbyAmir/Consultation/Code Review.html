AI Code Review Playbook

How to decide how much AI-written code to read, what proof to demand from agents, and how to ship safely when you can't read everything.

Source: video transcript by John, senior staff software engineer at Meta, “Should you still read AI-generated code?” Restructured as a reference; the prompts and template are written from his points. New to a term? See Key terms.

Bottom line

Yes, still read code, but how much depends on the blast radius. Review effort is a dial, not a yes/no.
  1. Trunk code (shared state, infra, entry points, ungated production behavior): read it closely.
  2. Leaf code (isolated or fully behind a feature gate): skim it and trust the proof.
  3. Make agents prove their work with tests, logs, screenshots and a confidence level. More proof means less reading.
  4. Review with a fresh agent that never saw the build conversation. The builder agent grades its own work too kindly.
  5. Lean on safety over reading: feature gates, canaries and rollback let you undo bad decisions you didn't catch.

AI across the whole lifecycle

Review is one stage of four. How much review a change needs is decided mostly by what you did in planning and what you'll do at launch.

01

Plan

  • Agent drafts the spec
  • Define validation criteria and evals up front
  • Plan the feature gates
  • Separate leaf work from integration work
02

Build

  • Agents make small, atomic changes
  • Agentic validation: the agent runs tests, reads logs, fixes itself
03

Review

  • Depth set by blast radius
  • Proof attached to the PR
  • Independent reviewer agent
  • Lint and type checks handle nits
04

Launch

  • Launch-readiness audit
  • Gate, canary, A/B test
  • Watch crashes and alerts
  • Roll back if needed

Think of the codebase as a tree

Different parts of the tree carry different risk. Before reviewing, place the change on the tree.

TRUNK Read deeply

  • Main entry points (e.g. App.js and the helpers wired into it)
  • Infrastructure: networking, image processing and rendering pipelines
  • Shared state, e.g. a reducer action that many screens depend on
  • Any change to existing production behavior that isn't gated
  • Anything with many downstream dependencies

LEAF Skim and check the proof

  • One-off UI components, checked with component or snapshot tests
  • New logic, a new endpoint or an integration, checked with unit or integration tests
  • Anything fully behind a feature gate and not wired into production paths
  • Skim for anything obviously wrong, then move on
Why this works: a bug in a leaf hurts one feature that is already switched off. A bug in the trunk can break the whole app. Spend your attention where a mistake is expensive.
Know your codebase: the better you know it, the faster you can tell whether a diff touches a dangerous zone or a leaf. That skill gets more valuable as you read less code.

The three safety questions

QuestionWhat it tells you
What is the control experience that must not change?The baseline behavior your review protects. If the change can alter it, read more.
If this goes wrong, how bad is it?The size of the blast radius.
Can I roll it back?The most important one. If a gate flip undoes it, you can review much less.

Build behind feature gates from day one

Gating is what lets you read less code safely. It belongs in the plan, not added at the end.

PracticeHow
Start simpleA Boolean flag in config is enough to begin with. Move to a flag service (e.g. LaunchDarkly) when you need targeting and gradual rollout.
Gate in broad strokesWhen planning the feature, gate every new path, not just the risky one.
Isolate the leavesBuild new parts so they don't touch existing code. These get light review.
Gate the integration layerWhere new code plugs into the trunk is the dangerous spot. Plan it and gate it separately.
 
# Simplest possible gate: control path stays untouched
FEATURES = {"save_card": False}   # flip per env / per user later

def on_card_swipe(card, user):
    if FEATURES["save_card"]:
        return save_card_flow(card, user)   # new leaf code
    return legacy_swipe(card, user)         # control experience

Require proof in every PR

Push agents to show evidence that the change works. With proof up front, you read less code and believe the output more.

Proof typeWhat it looks likeHow you review it
Unit testsFocused tests for the logic changedRead test names and asserts. Watch for useless tests that assert nothing real.
Component / snapshot testsRender tests for UI leavesCheck the snapshot diff matches the intent.
Runtime evidenceLogs from an actual run of the featureScan for the expected events and no errors.
Visual evidenceScreenshot or short video of the UI working (e.g. the new Save button saving a card)Look at it. Fastest trust signal for UI work.
Confidence levelAgent rates its confidence per area: logic, gating, integrationRead the low-confidence areas closely.
Tip: agents love to write filler tests. Write a skill or rule that tells them what a useful test is, and bake the proof requirements into your PR skill so you don't have to ask every time.

Use agents as reviewers, the right way

AI is already a strong reviewer, probably better than most humans. Most people get poor results because of how they run it.

Do thisWhy
Use a fresh, independent reviewerThe agent that wrote the code anchors on its own conversation and goes easy on itself. Use a new sub-agent, or a different agent entirely, with no build context: an adversarial reviewer.
Start from a good review skillBuilt-ins are solid: /code-review in Claude Code, the review agent in Codex.
Add a reviewer on GitHubCodex can be added as a GitHub reviewer that runs on every new PR or when tagged. It uses a model tuned for review. It costs money.
Let static checks own the nitsLinting, type checking and formatters, plus the review agent, handle style. Personal style debates no longer belong in code review: code changes fast and refactors are cheap once validation exists.
Use a PR templateWithout one the agent writes a long story. A template makes every PR look the same and keeps the important parts.
Automate the comment loopSet up a recurring task that checks the PR every hour, fixes reviewer comments, reruns validations, updates notes and re-pushes.
Pet peeve to avoid: a PR whose summary and test plan are longer than the code change itself.

Adversarial reviewer (run in a fresh session or sub-agent)

You are an independent code reviewer. You did not write this code and have
no context from the conversation that produced it. Assume it has bugs.

Review the diff in <PR / branch>. Report only real problems, most severe first.

1. Classify each changed file as TRUNK (entry points, infra, shared state,
   ungated production behavior) or LEAF (isolated or fully feature-gated).
2. For TRUNK files: check side effects on existing behavior, downstream
   callers, concurrency, error handling and security.
3. Check the feature gate: with the flag OFF, is the control experience
   exactly unchanged? Can the change be rolled back by flipping it?
4. Check the proof: do the tests assert real behavior, or are they filler?
   Is anything claimed in the PR description not backed by evidence?
5. Ignore style nits that lint or the type checker would catch.

For each finding give: file:line, what breaks, a concrete failing scenario,
and a suggested fix. End with: SAFE TO MERGE / NEEDS CHANGES / NEEDS HUMAN
REVIEW (name the files a human must read).

PR babysitter (recurring task)

Babysit PR <link>. Every hour until it is approved or I tell you to stop:
1. Read new review comments, including from the Codex/AI reviewer.
2. Fix each valid request. If you disagree, reply with your reasoning
   instead of changing code.
3. Rerun local validation: lint, typecheck, unit and integration tests,
   plus the agentic checks (run the feature, capture logs/screenshots).
4. Update the PR description so the Proof and Confidence sections match.
5. Push and re-request review. Stop and ping me if a fix touches trunk
   code or the feature gate.

Launch-readiness audit

Audit the full feature <name> (all merged PRs behind flag <flag>) before launch.
Look at it as a whole, not diff by diff. Report on:
- Does it work to spec? List any spec item that's missing or partial.
- Bugs and edge cases across the combined changes.
- Performance: hot paths, extra renders, N+1 calls, payload size.
- Security: input validation, auth checks, secrets, injection.
- Cleanup: dead code, duplicated helpers, leftovers from fast iteration.
Rank findings by launch risk.

Merge-ready is not launch-ready

Working this way, everything gated and landed gets you about 80% of the way. The last 20% takes about as long as the first 80%, and it's where human taste matters most.

80% broad strokes: agents build, gated, merged
20% polish
PhaseWhat happensWho leads
Broad strokesAgents build fast, everything gated and landed, light review on leavesagents
Launch-readyWhole-feature audit by agents (spec, bugs, performance, security), refactoring and cleanup, details such as animationsyou

The big idea: build an “agentic garden” around your code: lots of tests, validation and reviewing agents, plus gates so you can take back bad decisions. You can't physically read everything anymore, so safety has to come from the system.

Interview answer: “Do you still read AI-generated code?”

Short version (~30 s): “Yes, but the depth depends on blast radius. I treat the codebase like a tree. Trunk changes such as shared state, infra or ungated production behavior, I read line by line. Leaf changes that are isolated or behind a feature gate, I skim, as long as the PR carries proof: tests, runtime logs, a screenshot, and the agent's confidence per area.”

If they push: “Reviews run with a separate agent that has no context from the build session, because the builder anchors on its own reasoning. Lint and type checks handle style. And the real safety net is at launch: everything ships behind a gate, goes out as a canary, and rolls back with a flag flip. That's what lets me read less without taking on more risk.”

Summary in plain words

When AI writes your code, you don’t have to read every line, but you can’t skip reading either. How much you read depends on how much could break. Think of your code as a tree. The trunk is the important code that the whole app depends on, so a bug there can break everything, and you read it carefully. The leaves are small, separate pieces, so a bug there only breaks one small thing, and a quick look is enough. Before you trust the AI’s code, ask it for proof that it works: tests, logs, or a screenshot. Then have a different AI check the code, because the AI that wrote it is too easy on its own work.

The other big idea is to make every change easy to undo. Put new features behind an on/off switch (a “feature gate”). When you release, turn the feature on for a few users first. If something breaks, flip the switch off and the problem is gone. Merging the code is only about 80% of the job. The last 20% is your own final check and polish before real users see it. So the simple rule is: read more where mistakes are expensive, read less where they’re cheap, and always keep a way to undo.
