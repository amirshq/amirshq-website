Software Architecture Decision Sheet

Pick the architecture at project start based on criteria, not trends. One page, three layers, one flowchart.

1. First: these are three different decisions

Common confusion: SOLID is not an alternative to microservices. They live at different levels. You choose one deployment style, one internal structure, and you apply principles everywhere.
LevelQuestion it answersOptionsDecided whenCost to change later
A. Architectural style
(system level)		How many deployable units? How do they talk?Monolith · Modular monolith · Microservices · Serverless · Event-drivenProject startHigh
B. Internal structure
(codebase level)		How is code inside one unit organized?Layered (N-tier) · Hexagonal (ports & adapters) · Clean / Onion · CQRS · Vertical slicesProject start, per serviceMedium
C. Design principles
(class / module level)		How do I write each piece so it stays changeable?SOLID · DRY · KISS · YAGNI · Separation of concerns · High cohesion / low couplingAlways, every PRLow (refactor)

PatternIdeaUse whenAvoid when
Layered (N-tier)API → Service → Repository → DBCRUD apps, small teams, simple logicComplex business rules (logic leaks across layers)
Hexagonal (Ports & Adapters)Core logic in the middle; DB, LLM, APIs plug in via interfacesMany external integrations, need to swap providers (OpenAI ↔ Azure), testabilityTiny scripts / throwaway PoCs

6. Design principles — apply in any architecture

PrincipleMeaning (plain)Smell when violated
SSingle ResponsibilityA module has one reason to change (one actor/owner)One class handles parsing, DB, and email
OOpen / ClosedAdd behavior by extending, not editing existing codeEvery new provider = edit a big if/elif
LLiskov SubstitutionA subtype must work anywhere the parent worksSubclass throws "not supported" for a parent method
IInterface SegregationSmall, specific interfaces over one fat oneClasses implement methods they don't use
DDependency InversionDepend on abstractions; inject concrete onesBusiness logic does OpenAI() directly
Separation of concernsKeep UI, logic, data, infra apartSQL inside API handlers
High cohesion / low couplingRelated things together; few links between modulesChange in one module breaks five others
DRYOne source of truth for each piece of knowledgeSame rule copied in 4 places
KISS / YAGNISimplest thing that works; don't build for imagined needsKafka + K8s for 50 users
12-FactorConfig in env, stateless processes, logs as streamsSecrets in code, local file state

7. Applied to AI / LLM projects (RAG, agents)

Start here

  • Modular monolith (FastAPI)
  • Hexagonal inside: ports for LLM, vector store, tools
  • Background worker + queue for ingestion

Split out when…

  • Ingestion / embedding load differs from query load
  • Self-hosted model needs GPU scaling
  • Eval pipeline runs on its own schedule

Don't

  • One microservice per agent "because agents"
  • Call the LLM SDK directly from route handlers
  • Share one DB across "independent" services

8. Record the decision (ADR — 5 lines)

Title · Context (criteria answers from section 3) · Decision (style + internal structure) · Consequences (what gets easier / harder) · Revisit trigger (e.g. "2nd team joins" or "ingestion > 10× query load")
Bottom line: start with a modular monolith with clean module boundaries and SOLID inside. It keeps you fast now, and good boundaries let you extract microservices later — when a real criterion forces it, not before.
